```js
// routes/users.js  (Express)
router.get('/users/:id', async (req, res) => {
  const user = await db.query('SELECT * FROM users WHERE id = ' + req.params.id);
  res.json(user);
});

router.post('/users', async (req, res) => {
  const u = req.body;
  db.query(`INSERT INTO users (email, role) VALUES ('${u.email}', '${u.role}')`);
  res.send('ok');
});
```

## Findings

### 🔴 BLOCKER
#### [B1] SQL built by string concatenation on GET and POST
**Dimension**: Security
**Location**: users.js:3, users.js:9
**Problem**: `req.params.id`, `u.email` and `u.role` are pasted into the SQL text.
**Risk**: attacker-controlled input changes the query itself — read, modify, or delete any row.
**Fix**: bound parameters: `db.query('SELECT id, email, role FROM users WHERE id = $1', [req.params.id])`; same for the insert.

#### [B2] Privilege escalation via client-set `role`
**Dimension**: Security (also why Validation mentions "see B2")
**Location**: users.js:9
**Problem**: `role` comes straight from the request body into the insert.
**Risk**: any caller creates an admin account by sending a `role` field.
**Fix**: never read `role` from the client; set the default server-side and change roles only through an authorized admin path.

### 🟠 MAJOR
#### [M1] POST write not awaited
**Dimension**: Async/Await
**Location**: users.js:9-10
**Problem**: `db.query(...)` isn't awaited; `res.send('ok')` runs before the insert finishes.
**Risk**: the client is told "ok" for inserts that fail (duplicate email, DB down); the rejection is unhandled.
**Fix**: `await` the insert and respond after it succeeds.

#### [M2] No error handling
**Dimension**: Error Handling
**Location**: users.js:2-5, users.js:7-11
**Problem**: no try/catch or async error middleware.
**Risk**: a failed query leaves the request hanging or returns the framework's default error page, with details, depending on Express version and config.
**Fix**: an async error wrapper or middleware that logs server-side and returns one error shape.

#### [M3] No input validation at the boundary
**Dimension**: Validation
**Location**: users.js:3 (`id`), users.js:9 (`email`)
**Problem**: `id` isn't checked to be an integer/UUID; `email` isn't checked at all.
**Risk**: malformed ids reach the database as 500s; invalid emails are stored.
**Fix**: validate `id` format and `email` with the project's validator before touching the DB; reject with 400/422.

### 🟡 MINOR
#### [m1] Create endpoint contract
**Dimension**: API Design
**Location**: users.js:10
**Problem**: returns 200 with text `'ok'`; no `201`, no `Location`, no created resource.
**Fix**: `res.status(201).location(`/users/${id}`).json(created)`.

#### [m2] SQL inside route handlers
**Dimension**: Architecture
**Location**: users.js:3, users.js:9
**Fix**: fine at two routes; move to a small data-access module once a third query or a second caller appears.

## Questions
- Is there auth middleware in front of this router? If not, B1/B2 are anonymous — no change to scores, but it raises the urgency. (Security)
- Does `users` hold a password hash? The original `SELECT *` would return it to any caller — that would add a BLOCKER under Security.

## What's Good
- Routes are short and readable; the GET path uses async/await correctly.

## Action Plan
1. Parameterize both queries and stop reading `role` from the client — closes B1, B2 (~30 min).
2. Await the insert and add an async error middleware with one error shape — closes M1, M2 (~30 min).
3. Validate `id` and `email` at the boundary — closes M3 (~20 min).
4. Return 201 + Location on create — closes m1 (~10 min).
