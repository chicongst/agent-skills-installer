# Example: /document-review

## User Input (document to review)

```markdown
# Deployment Process

Our deployment process is designed to be robust and seamless, leveraging
best-in-class tooling to empower the team.

## Steps

1. Merge your PR.
2. The pipeline runs.
3. Verify the deploy looks good.
4. Notify the team.

## Rollback

If something goes wrong, roll back.

## Notes

Deployments happen twice a day. The release window is 10:00-11:00.
Only the on-call engineer can approve a release. See the runbook for details.
Deploys are limited to one per day to reduce risk.
```

## Skill Output

# Document Review: Deployment Process

**Type**: Process guideline
**Audience**: assumed — newcomer with no project context (not stated in the doc)
**Findings**: 🔴 3 · 🟠 4 · 🟡 2 · 💭 0
**Verdict**: Not ready — a new engineer following this would deploy without approval and could not roll back.

## Summary
This reads as a reminder for someone who already knows the process, not as instructions
someone else can follow: three of four steps are not executable, Rollback has no
procedure, and Notes contradicts itself on deploy frequency. The numbered-step shape is
right; it needs the missing detail.

## Findings

### 🔴 BLOCKER
#### [B1] Rollback section contains no procedure
**Location**: Rollback
**Problem**: "If something goes wrong, roll back" restates the heading. The reader who
opens this section during an incident gets no trigger, no command, and no one to tell.
**Fix**:
```
Roll back when [TODO: owner to supply — metric and threshold, e.g. error rate > X% for Y min].

1. Run `[TODO: owner to supply — rollback command]`
2. Confirm [TODO: health check or dashboard] is back to normal
3. Post in [TODO: channel] with the service name and the version rolled back to
```

#### [B2] Step 3 has no success criteria
**Location**: Steps > item 3
**Problem**: "Verify the deploy looks good" gives no checks, so the reader will either
approve a broken deploy or block a healthy one.
**Fix**: Replace with named checks: "3. Verify: [TODO: health endpoint] returns 200;
[TODO: dashboard] error rate stays below [TODO: threshold] for [TODO: minutes];
no new errors in [TODO: log location]."

#### [B3] Contradiction on deploy frequency
**Location**: Notes (sentences 1 and 4)
**Problem**: "Deployments happen twice a day" and "Deploys are limited to one per day"
cannot both be the policy; the reader can't tell which applies.
**Fix**: Keep one sentence. If both hold under different conditions, name the
condition, e.g. "Scheduled deploys: [TODO: times]. Hotfixes: [TODO: limit]."

### 🟠 MAJOR
#### [M1] Approval and release window are not in the steps
**Location**: Notes vs Steps
**Problem**: Only the on-call engineer can approve, and the window is 10:00–11:00, but
the numbered steps never say so — a reader following them in order merges any time,
unapproved.
**Fix**: Add a step 0: "Before merging: it is between 10:00 and 11:00 [TODO: timezone],
and the on-call engineer has approved in [TODO: where approval is recorded]."

#### [M2] Step 2 hides the whole pipeline
**Location**: Steps > item 2
**Problem**: "The pipeline runs" doesn't say where to watch it, how long is normal, or
what failure looks like.
**Fix**: "2. The CI pipeline runs ([TODO: stages], usually [TODO: duration]). Watch it at
[TODO: link]. A failed stage stops the deploy — go to Rollback."

#### [M3] "The runbook" is an unresolvable reference
**Location**: Notes (sentence 3)
**Fix**: Link the runbook by name and URL, or delete the sentence.

#### [M4] Step 4 has no recipient
**Location**: Steps > item 4
**Fix**: "4. Post in [TODO: channel]: service, version, link to the pipeline run."

### 🟡 MINOR
#### [m1] Opening paragraph is filler
**Location**: Intro
**Fix**: Replace with the purpose: "How to deploy a service to production and roll it
back if it fails."

#### [m2] Scope never stated
**Location**: (document-wide)
**Fix**: One line under the title naming the services this covers and who it is for.

## Checked
- No commands, paths, or links to verify — the document contains none (itself part of B1/B2).

## What works
- Numbered steps are the right format for this content.
- Rollback has its own section, so it is findable under pressure once it has content.

## Top priorities
1. Write the rollback procedure — B1
2. Replace "looks good" with concrete checks — B2
3. Resolve the deploy-frequency contradiction — B3
4. Put the window and approval into the steps — M1
