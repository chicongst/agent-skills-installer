# Example: /performance-review

## User Input
Our product search endpoint is slow. GET /api/products/search?q=shoes&category=footwear
is our most-used endpoint (~50k requests/hour). Target: p99 < 500 ms.

Production APM, last 7 days: p50 640 ms, p95 2.1 s, p99 3.8 s, max 8.1 s. The DB span
is ~90% of request time in the slowest traces. Latency varies by search term.

PostgreSQL 17. products: 2.0M rows (70,303 in footwear). reviews(id, product_id, rating,
created_at): 8.0M rows.
Indexes: products(category_id), reviews(product_id), categories(slug) unique.
Writes: ~3,000 new reviews/day; a nightly import updates ~50k product rows.

Query (from ProductSearchRepository):
```sql
SELECT p.*, c.name as category_name, AVG(r.rating) as avg_rating
FROM products p
LEFT JOIN categories c ON p.category_id = c.id
LEFT JOIN reviews r ON r.product_id = p.id
WHERE p.active = true
  AND (p.name ILIKE '%shoes%' OR p.description ILIKE '%shoes%')
  AND c.slug = 'footwear'
GROUP BY p.id, c.name
ORDER BY avg_rating DESC NULLS LAST
LIMIT 20;
```

On a staging restore of production data, we ran it 4 times: 697, 496, 441 and 552 ms.

## Skill Output

# Performance Review: GET /api/products/search

## Baseline
- **Operation & rate**: product search, ~50k req/hour (~14 req/s on average; peak rate not given). This is the most-used endpoint.
- **Latency**: production APM, 7 days: p50 640 ms / p95 2.1 s / p99 3.8 s (max 8.1 s).
- **Target**: p99 < 500 ms (stated). Even today's p50 (640 ms) is above it.
- **Environment**: the plan comes from a staging restore of production data, one term ('shoes'), and a warm cache (`Buffers: shared hit` only, no `read`). The 4 runs took 441–697 ms.

## Measurement Gaps
- **Most of the production p99 is unexplained.** The warm staging query takes at most 697 ms, but production p99 is 3.8 s. The plan explains the problem for 'shoes' but not the tail. Candidates and how to capture each:
  - Cold cache: this plan made 194,500 buffer accesses. Rerun on staging after a restart and compare `shared read`.
  - Other search terms: only 'shoes' was measured. Take the 20 slowest distinct `q` values from APM, and include one term with no matches.
  - Pool or lock wait under concurrency: check the APM for a connection-acquire span, and look for `wait_event` in `pg_stat_activity` during a slow window.
- **Production plans**: load `auto_explain` (through `shared_preload_libraries` or `session_preload_libraries`). Set `auto_explain.log_min_duration = '1s'`, `log_analyze = on`, `log_buffers = on`, and `log_timing = off` (lower overhead), with `sample_rate` if needed. This logs the plans the slow requests actually got.
- **Peak request rate**: needed to size the load test. Ask the user.

## Where the Time Goes
Source: the 552 ms staging plan. `actual time` values are inclusive and per loop.

| Phase | Measured time | Share | Source |
|---|---|---|---|
| Read 70,303 footwear rows, apply `ILIKE` + `active` filter (keeps 20,155) | 279 ms | 50% | Bitmap Heap Scan on products |
| 20,155 index lookups into reviews (80,918 rows) | ≈214 ms (495.9 − 282.4) | 39% | Nested Loop Left Join; 141,010 buffers |
| Sort by p.id, GROUP BY, AVG, top-N sort | ≈57 ms (552.5 − 495.9) | 10% | Sort / GroupAggregate / Limit |
| Planning | 1 ms | <1% | Planning Time |

The planner estimated 190 product rows and got 20,155. Because the category is joined by slug, the planner cannot use the statistics for category 'footwear' (actual 70,303 rows; the planner estimated 10,000).

## Findings

### 🟠 Rating aggregated per request over every matching product
- **Evidence**: the reviews lookups plus aggregation account for ≈270 ms (552.5 − 282.4; 49%) of 552 ms. The query must aggregate all 20,155 matches before it can pick the top 20 by rating. This finding leads although the ILIKE scan is larger (50%): for broad terms its fix also removes most of that 279 ms scan, because the rating-ordered index walk stops after 20 matches.
- **Hypothesis**: ratings change slowly (~3,000 reviews/day), so computing them on every search is repeated work. It also prevents an index from delivering rows already ordered by rating.
- **Fix**: store the aggregate on the product and index it for this access path:
  ```sql
  SET lock_timeout = '3s';
  -- numeric(3,2) assumes ratings on a 1–5 scale (max 9.99)
  ALTER TABLE products ADD COLUMN rating_avg numeric(3,2),
                       ADD COLUMN review_count integer NOT NULL DEFAULT 0;
  RESET lock_timeout;

  -- Backfill in PK batches, one transaction each; a script advances :lo by 50000 up to max(id)
  UPDATE products p
     SET rating_avg = s.avg_rating, review_count = s.cnt
    FROM (SELECT product_id, round(avg(rating), 2) AS avg_rating, count(*) AS cnt
            FROM reviews
           WHERE product_id > :lo AND product_id <= :lo + 50000
           GROUP BY product_id) s
   WHERE p.id = s.product_id AND p.id > :lo AND p.id <= :lo + 50000;

  CREATE INDEX CONCURRENTLY products_active_cat_rating_idx
      ON products (category_id, rating_avg DESC NULLS LAST) WHERE active;
  ```
  Query after the change (the reviews join and GROUP BY are removed, and the category id is resolved first; see the 🟡 finding below):
  ```sql
  SELECT p.id, p.name, [other columns the API returns], p.rating_avg, p.review_count, c.name AS category_name
  FROM products p
  JOIN categories c ON c.id = p.category_id
  WHERE p.active
    AND (p.name ILIKE '%' || $1 || '%' OR p.description ILIKE '%' || $1 || '%')
    AND p.category_id = $2
  ORDER BY p.rating_avg DESC NULLS LAST
  LIMIT 20;
  ```
  Keep the columns current with a job every 10 minutes. It recomputes products whose reviews were created since the last run. A nightly batched full recompute catches deletions.
- **Expected gain**: estimate. It removes the ≈270 ms reviews and aggregation phases. For a broad term the planner can walk the new index in rating order and stop after 20 matches. 20,155 of 70,303 footwear rows match 'shoes', so it would read roughly 70 rows instead of 70,303. Rare terms still scan the whole category (see the next finding).
- **Cost**: two columns and one partial index (measure its size with `pg_relation_size` on staging). The backfill writes a new version of every product row that has reviews, so the table bloats until vacuum reclaims the space. Every rating refresh also updates all of the products indexes.
- **Rollout risk**: low with mitigations. Both `ADD COLUMN`s are metadata-only (nullable, or a constant default), but they still need a brief ACCESS EXCLUSIVE lock, hence `lock_timeout`. The backfill is batched, and you can `VACUUM products` between batches while watching replica lag. The index is built `CONCURRENTLY`, outside a transaction. Deploy the query change only after the backfill finishes. Rollback: revert the query, and the new columns are harmless. Hand the runbook to `migration-safety`.
- **Behavior change**: yes, needs product sign-off.
  - (1) The rating is rounded to 2 decimals in the API response (it was full precision), and near-equal ratings can reorder.
  - (2) Ratings lag new reviews by up to 10 minutes, and deleted reviews until the nightly recompute.
- **Verify**: on staging, diff the new query's rows and ratings against `round(AVG(...), 2)` from the old query. Only tie order may differ. Then run `EXPLAIN (ANALYZE, BUFFERS)` for 'shoes'. It passes if it shows `Index Scan using products_active_cat_rating_idx` under `Limit`, with no reviews node. If the plan shows Bitmap Heap Scan + Sort instead, the planner underestimates the ILIKE matches — compare estimated vs actual rows, raise `SET STATISTICS` on name/description and re-`ANALYZE`, or rely on the trigram finding.

### 🟠 Leading-wildcard ILIKE is evaluated on every row in the category
- **Evidence**: the Bitmap Heap Scan on products takes 279 ms (50%) and discards 50,148 of 70,303 rows. A B-tree index cannot serve `ILIKE '%…%'`, so the category index is the only filter available.
- **Hypothesis**: terms that match few rows are the worst case. After the first fix, the rating-ordered walk finds no early matches for them and reads the whole category. This may explain part of the "latency varies by search term" in production, but that is unmeasured (see Measurement Gaps).
- **Fix (keeps semantics)**: trigram indexes, which can serve `ILIKE '%term%'`:
  ```sql
  CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- needs a role allowed to create extensions
  CREATE INDEX CONCURRENTLY products_name_trgm_idx        ON products USING gin (name gin_trgm_ops);
  CREATE INDEX CONCURRENTLY products_description_trgm_idx ON products USING gin (description gin_trgm_ops);
  ```
- **Expected gain**: estimate. For selective terms the planner can combine the two indexes (BitmapOr) and skip the category scan. Terms shorter than 3 characters produce no trigrams and get no benefit.
- **Cost**: GIN index size and build time are unknown for 2M descriptions, so measure them on staging. GIN also slows writes, which matters for the nightly 50k-row import.
- **Rollout risk**: low. The indexes are built `CONCURRENTLY`, one at a time, off-peak. Rollback: `DROP INDEX CONCURRENTLY`.
- **Behavior change**: none. It returns the same rows as today.
- **Verify**: `EXPLAIN (ANALYZE, BUFFERS)` for a rare term and for 'shoes'. The rare term should use `Bitmap Index Scan on products_*_trgm_idx`. Then run the load test with the production term mix.
- **Alternative (changes behavior)**: full-text search (`to_tsvector @@ plainto_tsquery`) matches words, not substrings. With the 'english' configuration, 'shoes' stops matching "snowshoes" and "Shoeshine" and starts matching "shoe rack" through stemming. Adopt it only as a product decision. If adopted, use an expression GIN index (`CREATE INDEX CONCURRENTLY … USING gin (to_tsvector('english', coalesce(name,'') || ' ' || coalesce(description,'')))`, and the query must repeat that exact expression). Do not add a STORED generated `tsvector` column: that rewrites the 2M-row table under an ACCESS EXCLUSIVE lock.

### 🟡 Category joined by slug hides its row count from the planner
- **Evidence**: the planner estimated 10,000 rows for the category and got 70,303, and 190 matches where there were 20,155.
- **Fix**: resolve `slug → id` first. The categories table has 200 rows and can be cached. Pass `category_id` into the query, as in the rewrite above.
- **Expected gain**: estimate. It gives the planner per-value statistics, so it can choose between the rating-ordered walk (broad terms) and the trigram bitmaps (rare terms).
- **Cost / Rollout risk**: one cached lookup, deployed with the query change. If the driver uses server-side prepared statements, PostgreSQL may switch to a generic plan after 5 executions. A generic plan cannot see the category or the term, so broad terms fall back to scanning the whole category. Check the production plans from `auto_explain`. If they are generic, set `plan_cache_mode = force_custom_plan` for this query's session or role.
- **Behavior change**: none. `LEFT JOIN categories` combined with `WHERE c.slug = …` already behaved as an inner join.
- **Verify**: the estimated rows for the products scan are within about 10× of the actual rows.

### 💭 Query hygiene
- **Evidence**: `SELECT p.*`. `ORDER BY avg_rating` has no tie-breaker, so the order among equal ratings is undefined today.
- **Fix**: select explicit columns (as in the rewrite). Adding `p.id` as a tie-breaker makes paging stable, but that is a behavior change (deterministic order), so ship it separately if wanted.

## Not Recommended
- **Elasticsearch/OpenSearch**: nothing measured so far shows PostgreSQL cannot meet 500 ms. It would add a second system to keep in sync. Revisit if relevance ranking, typo tolerance, or facets become requirements.
- **Caching search responses**: the hit rate depends on the distribution of search terms, which has not been measured. It also serves stale results (a behavior change). Revisit after the fixes if p99 still misses the target.

## Plan
1. Close the measurement gaps: enable `auto_explain`, measure pool wait, run cold-cache and rare-term plans, and get the peak request rate.
2. Build a load test against the staging restore at peak rate with a constant-arrival-rate generator, replaying the production term mix. Record the p50/p95/p99 baseline over 3 runs.
3. Apply the rating fix on staging: columns, batched backfill, index, query change, and the result diff. Re-run the load test.
4. If rare-term p99 still misses 500 ms, add the trigram indexes one at a time and re-run the load test.
5. Roll out in the same order, with `migration-safety` reviewing the DDL and backfill. Compare the production p99 against the 7-day baseline.
6. Guard against regressions: alert on p99 > 500 ms for this endpoint, and add a staging check that the 'shoes' plan still uses `products_active_cat_rating_idx`.
