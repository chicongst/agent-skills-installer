# PR Review: Add rate limiting to API

**Source**: pasted diff · **CI**: passing (lint, unit tests)

## Summary
Adds a Redis-backed limiter of 100 requests/minute per API key to every /api route. The
scope is right, but a Redis error on EXPIRE crashes the Node process, the PR quietly changes
the Redis client shared with sessions and cache, and the only test passes even when the
limiter does nothing. REQUEST CHANGES.

## Change Analysis
- **Scope**: Focused on rate limiting, except the shared-client change in config/redis.js (finding 2)
- **Size**: 4 files, +33 −1, all meaningful — reviewable
- **Hidden changes**: config/redis.js:2 changes connection behavior for every importer (session store, cache)
- **Risk**: High — runs on every /api request, a Redis error can crash the process, and the shared Redis client changes
- **Reversibility**: Revert-safe — no schema or persisted data; leftover `ratelimit:*` keys are unused after a revert
- **Description**: Missing Redis-failure behavior, the shared-client change, how it was tested, and rollback

## Findings

### 🔴 BLOCKER
#### 1. A Redis error on EXPIRE crashes the process — `middleware/rate-limit.js:13` [verified]
**Problem**: Express 4 ignores the promise returned by async middleware. If `redis.expire`
rejects (for example, the connection drops after INCR), the rejection is unhandled, and Node 22
exits on unhandled rejections by default. Reproduced: the app with EXPIRE stubbed to reject exited
with code 1 on the first request. Even without a crash, a failure between INCR (line 9) and EXPIRE
(line 13) leaves the key with no TTL, so once that key passes 100 it gets 429 forever.
Don't fix this with `.catch((err) => next(err))` on line 9: the function would carry on with
`current === undefined` and call `next()` a second time.
**Fix**: do INCR+EXPIRE in one atomic script and handle the error in one place:
```javascript
const INCR_WITH_TTL = `
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return current`;

module.exports = async function rateLimit(req, res, next) {
  const key = `ratelimit:${req.get('X-API-Key')}`;

  let current;
  try {
    current = await redis.eval(INCR_WITH_TTL, 1, key, WINDOW_SECONDS);
  } catch (err) {
    console.error('rate-limit: Redis error, request not limited', err); // use the project's logger
    return next(); // fail open; to fail closed, respond with res.status(503) instead (see Question 1)
  }

  if (current > LIMIT) {
    res.set('Retry-After', String(WINDOW_SECONDS));
    return res.status(429).json({ error: { code: 'RATE_LIMIT_EXCEEDED' } });
  }
  return next();
};
```
Verified: every path calls `next()` or sends a response exactly once. With Redis failing,
the request gets 200 and the process stays up. The tests in finding 4 pass once findings 1 and 2
are both fixed.

### 🟠 MAJOR
#### 2. Undisclosed change to the shared Redis client — `config/redis.js:2` [verified]
**Problem**: `enableOfflineQueue: false` makes every command sent while the client is
connecting or reconnecting reject immediately ("Stream isn't writeable and enableOfflineQueue
options is false") instead of waiting. Reproduced: with this option, an INCR sent right after
`new Redis(...)` rejected with that error; with the default client it was queued and succeeded. This client is also used by the session store and the
cache, so their behavior during startup and Redis reconnects changes. The description doesn't
mention this, and the diff doesn't show whether they handle the rejection. For the limiter
itself, requests that arrive before the connection is ready are not rate limited (line 10).
**Fix**: Revert line 2. If the limiter needs to fail fast, give it its own client
(`new Redis(process.env.REDIS_URL, { enableOfflineQueue: false })` in the limiter module) and
leave the shared client unchanged.

#### 3. A Redis outage silently turns rate limiting off — `middleware/rate-limit.js:9-10`
**Problem**: Any Redis error lets the request through with no log or metric. A Redis outage
removes rate limiting with nothing to show for it, and the fail-open choice is not documented.
**Fix**: Log (or count) the failure, as in the fix for finding 1. Record the fail-open or
fail-closed decision in the code comment and the PR description (Question 1).

#### 4. The test doesn't exercise the limiter — `tests/rate-limit.test.js:5-8` [verified]
**Problem**: The only test sends one request and expects 200. It still passes with Redis
unreachable, which is the same as having no limiter. Nothing tests the 101st request, the
429 body, or the Redis-failure path.
**Fix** (add to the existing test file; passes with a real Redis once findings 1 and 2 are fixed —
with `enableOfflineQueue: false` still set, `redis.del` in `beforeEach` rejects before the client is ready):
```javascript
const redis = require('../config/redis');

beforeEach(() => redis.del('ratelimit:test-key'));
afterAll(() => redis.quit());

it('rejects the 101st request in a window with 429', async () => {
  for (let i = 0; i < 100; i++) {
    await request(app).get('/api/data').set('X-API-Key', 'test-key').expect(200);
  }
  const res = await request(app).get('/api/data').set('X-API-Key', 'test-key');
  expect(res.status).toBe(429);
  expect(res.headers['retry-after']).toBe('60');
});

it('lets the request through when Redis fails (fail-open policy)', async () => {
  jest.spyOn(redis, 'eval').mockRejectedValueOnce(new Error('connection lost'));
  const res = await request(app).get('/api/data').set('X-API-Key', 'test-key');
  expect(res.status).toBe(200);
});
```

### 🟡 MINOR
#### 5. 429 response has no Retry-After — `middleware/rate-limit.js:17`
**Problem**: RFC 6585 §4 says a 429 response MAY include `Retry-After`. Without it, clients
have to guess how long to back off.
**Fix**: Covered by the fix for finding 1. `WINDOW_SECONDS` is an upper bound; send the key's
remaining TTL if clients need the exact value.

#### 6. The description leaves out what a reviewer needs — (PR-wide)
**Problem**: It says what the limit is, but not what happens when Redis fails, that the shared
client changed, how it was tested, or how to roll back.
**Fix**: Add those four points. Rollback is simply reverting the PR.
